The Wizzit API uses standard HTTP status codes to indicate the outcome of every request. When a request fails, the response body is a JSON object with a consistent structure that tells you exactly what went wrong, which field caused the problem (when applicable), and a machine-readable error code you can use to drive error-handling logic in your integration.

## Error Response Format

All error responses set `success` to `false` and include an `error` object containing a `code`, a human-readable `message`, and an optional `details` array for field-level validation errors.

```json
{
  "success": false,
  "error": {
    "code": "invalid_params",
    "message": "The 'title' field is required.",
    "details": [
      { "field": "title", "issue": "required" }
    ]
  }
}
```

The `details` array is present when the error relates to specific request parameters — most commonly on `400` and `422` responses. Each entry identifies the offending `field` and describes the `issue`. For errors that are not field-specific (for example, `401` or `500`), `details` is omitted.

## HTTP Status Codes

| Status | Meaning                                                                                                  |
|--------|----------------------------------------------------------------------------------------------------------|
| `200`  | **OK** — The request succeeded. The `data` field contains the result.                                    |
| `201`  | **Created** — A new resource was successfully created. The `data` field contains the new resource.        |
| `204`  | **No Content** — The request succeeded but there is no response body (e.g., a successful DELETE).         |
| `400`  | **Bad Request** — The request was malformed or missing required parameters.                               |
| `401`  | **Unauthorized** — No valid API key was provided, or the key has been revoked.                            |
| `403`  | **Forbidden** — The API key is valid but lacks the required scope for this operation.                     |
| `404`  | **Not Found** — The requested resource does not exist or is not accessible with your credentials.         |
| `409`  | **Conflict** — The request conflicts with the current state — for example, a duplicate resource.          |
| `422`  | **Unprocessable Entity** — The request was well-formed but failed semantic validation.                    |
| `429`  | **Too Many Requests** — You have exceeded the rate limit of 100 requests per minute.                      |
| `500`  | **Internal Server Error** — An unexpected error occurred on Wizzit's servers. Retry with backoff.         |

## Error Codes Reference

| Code                | HTTP Status | Description                                                                       |
|---------------------|-------------|-----------------------------------------------------------------------------------|
| `invalid_params`    | `400`       | One or more request parameters are missing, malformed, or have an invalid value.  |
| `invalid_api_key`   | `401`       | The API key is missing, invalid, expired, or has been revoked.                    |
| `insufficient_scope`| `403`       | The API key does not have the required scope to perform this operation.            |
| `not_found`         | `404`       | The requested resource could not be found in your workspace.                      |
| `already_exists`    | `409`       | A resource with the same unique identifier or name already exists.                |
| `rate_limited`      | `429`       | The request was rejected because the rate limit has been exceeded.                |
| `server_error`      | `500`       | An internal error occurred. The request may succeed if retried after a short wait.|

## Handling Errors

Your integration should handle errors explicitly by checking the HTTP status code and, where appropriate, branching on the `error.code` value. Below are examples in JavaScript and Python.

**JavaScript**

```javascript
async function fetchDocuments(apiKey) {
  try {
    const response = await fetch("https://api.wizzit.com/v1/documents", {
      headers: {
        Authorization: `Bearer ${apiKey}`,
        "Content-Type": "application/json",
      },
    });

    const body = await response.json();

    if (!response.ok) {
      const { code, message } = body.error;

      if (code === "invalid_api_key") {
        throw new Error("API key is invalid or has been revoked.");
      } else if (code === "rate_limited") {
        // Retry after the reset window — see X-RateLimit-Reset header
        throw new Error("Rate limit exceeded. Please retry shortly.");
      } else {
        throw new Error(`API error [${code}]: ${message}`);
      }
    }

    return body.data;
  } catch (err) {
    console.error("Request failed:", err.message);
    throw err;
  }
}
```

**Python**

```python
import requests

def fetch_documents(api_key):
    try:
        response = requests.get(
            "https://api.wizzit.com/v1/documents",
            headers={
                "Authorization": f"Bearer {api_key}",
                "Content-Type": "application/json",
            },
        )
        body = response.json()

        if not response.ok:
            code = body["error"]["code"]
            message = body["error"]["message"]

            if code == "invalid_api_key":
                raise ValueError("API key is invalid or has been revoked.")
            elif code == "rate_limited":
                raise RuntimeError("Rate limit exceeded. Please retry shortly.")
            else:
                raise RuntimeError(f"API error [{code}]: {message}")

        return body["data"]

    except requests.exceptions.RequestException as e:
        print(f"Request failed: {e}")
        raise
```

<Tip>
  For `429 Too Many Requests` and `500 Internal Server Error` responses, implement **exponential backoff** — wait a progressively longer interval before each retry (for example, 1 s, 2 s, 4 s, 8 s) up to a maximum number of attempts. Check the `X-RateLimit-Reset` header on `429` responses to know exactly when your rate limit window resets before retrying.
</Tip>
